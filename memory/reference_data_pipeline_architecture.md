Full pipeline spans several repos/locations, none of which live in `C:\project\Apolo11` itself:

- **Glue/Spark jobs**: `C:\project\datalake-glue` (git repo, Bitbucket `ctv-ti/datalake-glue`). Core jobs `jdbc_to_bronze.py`, `bronze_to_silver.py`, `silver_to_gold.py` write execution status to Athena tables `tb_log_job_exec` (one row per execution_id), `tb_log_exec` (one row per table/layer, `status` = SUCESSO/ERRO, has `mensagem`/`stacktrace`), `tb_log_job_exec_hist`, all in Glue Catalog database `{env}_gold` (S3 `cootravale-layer-gold`). `bronze_to_silver.py` acts as a circuit-breaker: queries `tb_log_exec` for `status='ERRO' and camada='BRONZE'` on the current execution_id before proceeding.
- **Airflow**: self-hosted on EC2 (`ip-192-168-168-69`, `sa-east-1`, not MWAA), Airflow 3.1.7, Simple Auth Manager (admin password not documented). Metadata DB is external Postgres at `172.31.28.247:5432`, database `airflow_db`. DAG source is `C:\project\airflow-prod-dags` (git, synced to the EC2 via a 1-min cron `git pull`, no CI/CD). Main DAG `prd_carga_diaria_split_fluxo_datalake` (cron `0 4,14,19 * * *`) uses `GlueJobOperator` for bronze(x5)->silver->gold, then `TriggerDagRunOperator` chains to `hml_carga_diaria_fluxo_datalake`. **No alerting configured anywhere** (no `on_failure_callback`, email, Slack, SNS) except `pbi_enterprise_refresh` DAG which has `retries=2`.
- **Power BI governance BI**: `C:\PowerBIClaudio\3 - TI\Cootravale Governança.pbip` — NOT "Torre de Controle" (that's a separate GPS/logistics BI, see [[reference_torre_controle_docs]]). Its `Atualizacao_dataset` table (Status/ErrorMessage/StartTime/EndTime) is Import-mode from Excel in `CaminhoPastaExcel = C:\API_POWER_BI\Arquivos_excel\` (mirrored locally at `C:\project\api_powerbi_shell\api_power_bi\Arquivos_excel\`).
- **PowerShell governance pipeline**: `C:\project\api_powerbi_shell\api_power_bi\Orchestrator_Master.ps1` runs 6 phases via Power BI Admin REST API (`Connect-PowerBIServiceAccount`/`Invoke-PowerBIRestMethod`); Phase 6 (`Gerar atualizacao dataset.ps1`) queries `refreshSchedule`/`refreshes` per dataset and writes `Relatorio_Atualizacao_Datasets.xlsx`, the source for `Atualizacao_dataset`. Sibling project `C:\project\api-powerbi\scripts_powerbi_extract` has additional ad-hoc refresh-history extraction scripts.
- **MCP tool `servidor_transportadora`**: WSL `Ubuntu-22.04`, code at `/home/maia_rodrigo/agente-cooperado/servidor_mcp.py`. Exposes `list_athena_tables`, `describe_athena_table`, `run_athena_query`, `trigger_glue_job`, `list_s3_scripts`, `get_s3_script`. Known bugs: `list_s3_scripts`/`get_s3_script` pass the full `s3://bucket/prefix` URI as the `Bucket` param instead of just the bucket name (broken); `run_athena_query` polls with no timeout; `ATHENA_DATABASE` hardcoded to literal `"AwsDataCatalog"` (works for fully-qualified `schema.table` SQL, but `list_athena_tables`/`describe_athena_table` are effectively locked to that literal database name); AWS region hardcoded `us-east-1` regardless of `~/.aws` profiles; `trigger_glue_job` calls `boto3 start_job_run` directly, bypassing Airflow entirely — using it to "retry" a job leaves the Airflow DAG task stuck in failed state.

**How to apply:** any monitoring/alerting/automation work on this pipeline should read from `tb_log_exec`/`tb_log_job_exec` for Glue status, the Airflow Postgres metadata DB (if reachable) or REST API for DAG status, and `Relatorio_Atualizacao_Datasets.xlsx` (or the Power BI Admin API directly) for dataset refresh status. See [[project_pipeline_monitoring_agent]].

**Transient empty tables during the pipeline run:** on 2026-09-02, `prd_bronze.multi_dbo_t_cte` briefly returned 0 rows via Athena (`SELECT count(*)`) then recovered to 640k rows seconds later, while querying it via `mcp__servidor_transportadora__run_athena_query`. The user confirmed the DW pipeline was running at that moment, started ~16h. This conflicts with the `0 4,14,19 * * *` cron recorded above (16h isn't one of those slots) — either the schedule changed since this memory was last verified, or 16h is when a run that started at 14h reaches the step that overwrites that specific bronze table (the bronze->silver->gold chain can take ~2h). **How to apply:** any query/report run against `prd_bronze.*` tables (especially ones fed by `jdbc_to_bronze.py`) around the 14h/16h/19h window should tolerate a table read as unexpectedly empty and retry, rather than treating it as a data/query bug — this is very likely a live overwrite (Glue job rewriting the S3 location behind the Athena external table), not a real data-loss event. Verify current cron before relying on the exact hour.
